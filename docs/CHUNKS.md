# Synthetic source chunks

WORM-012 implements an independent local operation, not the complete candidate
pipeline. It creates small deterministic binary fixtures, splits them into
ordered chunks and reconstructs verified bytes. No Docker, external registry,
GitLab, Foreman, installation media or proprietary inputs are involved.
Candidate-derived payload/image binding belongs to WORM-013. These bytes are
named `.synthetic.bin`, never `.iso`. Production ISO eligibility and reference
release eligibility remain false.

Run from a clean committed checkout with Python 3.12. The workspace must be a
dedicated absolute path outside Git checkouts and vault synchronization paths.
Replace `WORKSPACE` below with that directory:

```text
python -m wormhole.chunks --workspace WORKSPACE --transport local
python -m wormhole.chunks --workspace WORKSPACE --transport http-loopback
python -m wormhole.chunks --workspace WORKSPACE --transport local --scenario corrupted
python -m wormhole.chunks --workspace WORKSPACE --acceptance
```

The first two commands return 0 for successful partial operations. The explicit
corruption operation returns 1 and retains its failure. Refused configuration,
storage or source identity returns 2. `--acceptance` executes twelve fresh Runs:
both transports with healthy, missing, duplicate, reordered, truncated and
corrupted scenarios. Its success means each expected outcome was observed;
the ten negative underlying operations remain failed. It emits machine-readable
results and stores the suite receipt in `evidence/chunk-acceptance.json` in its
own additional Run. Fixture definitions are [versioned JSON](../tests/fixtures/chunk-cases.json).

The Python API is `execute_fixture(run, ...)`, which owns the Run lock, followed
by `report_chunks(run)` or `verified_source(run)`. The module CLI creates new
real-mode Runs for these synthetic inputs. Linux uses the existing stable
kernel Run lock; Windows retains the existing exclusive lock and reports no
claim of verified POSIX permissions. No admission lease is needed because this
operation allocates no infrastructure. Disk storage is bounded to at most about
24 MiB of generated source, chunks and reconstructed bytes, plus small records.
The temporary reconstructed file becomes the output by rename, not by copying.

The complete-pipeline manifest remains unchanged with no claimed pipeline stages.
Read the component receipt for its terminal status; its passing status does not
complete the overall pipeline. The old CLI fixture's main artifacts and
`verify_run` remain unchanged.

## Contract and integrity boundary

[The generated schema](../schemas/chunk-manifest-v1.schema.json) comes from
`wormhole.chunks.schema()`. Structural validation uses the existing bounded
contract validator. Runtime additionally requires contiguous indices starting
at zero, exact offsets and indexed filenames, expected chunk counts and sizes,
and a separately retained canonical manifest SHA-256. It rejects reordered
records rather than sorting them and rejects duplicate indices. Repeated
content hashes are valid when different chunks contain identical bytes.

Each operation preserves:

- `evidence/chunk-plan.json`: source/Run identity, generation version, transport,
  declared fault, sizes, operation deadline and false eligibility flags.
- `evidence/chunk-original-manifest.json`: original ordered identities and hashes.
- `evidence/chunk-manifest.json`: the supplied reconstruction manifest, including
  an explicitly injected duplicate/order fault where selected.
- `evidence/chunks.json`: component outcome, bound plan/manifest hashes, verified
  chunk records, actual duration and safe failure code.
- `private/chunks/`: generated source, chunk files and verified reconstructed
  output only after successful verification. These files stay outside Git.

`verified_source(run)` is the candidate-consumer boundary. It requires a passing
component and rechecks saved manifest identities, original/reconstructed hashes,
size and complete chunk records. A failed, pending, modified or incomplete
operation cannot return candidate bytes. Reconstruction writes an exclusive
private partial file, checks every chunk hash/size and the total/whole-file hash,
checks source revision/deadline, then promotes it. Known failures remove only
that operation's partial file; an interrupted process may leave a private partial
file with a pending receipt, which cannot pass or be silently retried. Preserve
that Run and start a fresh one rather than adopting its files.

Hashes prove consistency against the recorded manifest, not independent origin
authenticity or resistance to a host administrator rewriting all records.

## Bounds and transports

Inputs are generated by fixed source code, 2 bytes to 8 MiB, with 2 to 256 chunks
of at most 1 MiB. An operation has a configured deadline of at most 30 seconds
(default 15). Reads and hashing stream through bounded buffers. Empty inputs and
one-chunk fixtures are explicitly unsupported by this initial fault fixture.

The local adapter requires the exact chunk filename set and ordinary private
owner files. Traversal, symlinks, junctions, hard links, extra files and existing
output are rejected. Source identity must remain the same clean commit.

The HTTP adapter starts one disposable server on `127.0.0.1` at an ephemeral
port and fetches only its fixed chunk paths. No caller-provided URL, hostname,
redirect, proxy, authorization or fallback source is accepted. Responses require
200, one exact Content-Length, no transfer encoding and the fixed content type.
The client uses `read1` with deadline checks around each receive; socket waits
are capped at 0.5 seconds and the server has its own bounded socket writes.
This is a lightweight local fixture, not a general HTTP download service.
The server is shut down after success or failure. `FutureRegistryAdapter` always
refuses: a real GitLab Generic Package Registry implementation is unverified.

## Verification

```text
python -m unittest discover -s tests -p test_chunks.py -v
python -m unittest discover -s tests -v
python scripts/verify_repository.py
```

Tests exercise both actual loopback/local transports, all five integrity faults,
manifest/receipt tampering, duplicate content hashes, source changes, interrupted
writes, linked paths, exact output protection, redirects, duplicate length
headers and a real slow loopback response. POSIX permission/link checks are
explicitly skipped on Windows and run on Linux. `--acceptance` is a real
generated-binary processing command; it demonstrates neither boot/install nor
candidate image mapping, full pipeline completion or publication eligibility.
